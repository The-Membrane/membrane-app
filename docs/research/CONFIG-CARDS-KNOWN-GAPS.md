# Config Cards: known gaps (2026-10-07, updated 2026-10-09, round 11: UQ-25 and its review)

This is the register of what the config cards do NOT do yet, after the final review round (round 8). The design is in [CONFIG-CARDS-DESIGN.md](CONFIG-CARDS-DESIGN.md).

**What gets fixed now and what goes here.** A confirmed bug that can make a dangerous change read calm, hide a red, or misstate chain data was fixed in round 8, and again in review round 9 (the review of the ruling #12–#14 work). Each one has a test that failed before the fix and passes now (`tests/unit/oracleRegistryConfigReview8.test.ts`, `tests/unit/oracleRegistryConfigReview9.test.ts`, for the review of the round-10 work `tests/unit/oracleRegistryConfigReview10.test.ts`, and for the review of the round-11 work `tests/unit/oracleRegistryConfigReview11.test.ts`). Everything else is listed here: cosmetic issues, latent issues, and anything that needs an owner call. Each entry has an id, the lens that found it, where it lives, what it does to the card, a proposed fix, and why it was not fixed now.

Line numbers are as of 2026-10-07 in the `feat/oracle-registry` worktree.

### KG-5: a timelock's constructor delay reads as a change from 0 s (older than round 11)

- **Lens:** on-chain (review round 11, a spot check).
- **Where:** the admin replay of `MinDelayChange`. In `changes/pt-srusde.json` the row "timelock 0xb2a3…b706 delay 0s → 86400s" at 23,049,699 is notes "delay INSTANT → 1d", severity upgrade. The row "timelock 0x68d8…77ac delay 0s → 172800s" at 25,481,956 is notes "delay INSTANT → 2d". Each is at its timelock's own deploy block (`subjects.json` `deployBlock`). The event is the OZ constructor's `MinDelayChange(0, d)`.
- **Impact:** the card shows a delay increase from an instant timelock that never existed: the contract had no code before that block. It misstates history, but no red is hidden and no dangerous change reads calm (the row is an upgrade, never red).
- **Proposed fix:** treat a `MinDelayChange` in the timelock's deployment transaction (or deploy block) as its initial delay, not as a change, and drop the row or label it "deployed with 1 d".
- **Why deferred:** it is older than this round, it is not one of the round-11 confirmed bugs, and the row is stored text: correcting it needs a PT-srUSDe re-collection (KG-4).

### KG-3: a parameter change reverted within one grid step can vanish between runs

- **Lens:** found while re-collecting the data in round 8. Same root cause as KG-1.
- **Where:** `scripts/oracle-registry/config/lib/params.mjs:106-118`. `paramTransitions` reads every declared getter on a 50,400-block grid that starts at `head − paramDays × 7,200`, and bisects only between grid points whose values differ.
- **Impact:**
  - A change that is undone before the next grid point (about 7 days) is invisible.
  - The grid moves with the head block, so whether such a change shows depends on the run. The card can lose a row it showed before.
  - Observed on weETH. The EtherFiOracle committee went 3 → 5 at 25,626,145 (a red MR-3 row; see UQ-2) and 5 → 3 at 25,633,016, 6,871 blocks apart.
  - Both rows were on the card at head 26,144,054. They are gone at head 26,145,153 (the round-8 re-run), because the new grid has no point between them.
- **Proposed fix:**
  - Replay the setter's own events where the contract emits them (the KG-1 fix covers the committees).
  - Anchor the grid at absolute multiples of the step, so that runs agree.
  - Carry transitions found by earlier runs forward, so a row never disappears.
- **Why deferred:** the reviewers did not raise this. The real fix is event replay, which is the same design work as KG-1.
- **Partly addressed 2026-10-08:** the committees now have event replay (KG-1, closed). A committee member change is a row of its own and no longer depends on the grid. The count rows (`oracleMembers`, `numActiveCommitteeMembers`) and every other grid parameter can still vanish between runs as described above.
- **Correction (review round 9):** the weETH quorum row 2 → 3 at 25,626,145 that the round-9 re-run lost was NOT this gap. It was CB-1: the weETH and wstETH param keys collided, so weETH's grid read wstETH's constant quorum 5 (fixed; see "Fixed in review round 9").

## Closed 2026-10-09 (round 11): UQ-25 — a token vote is judged against the trailing year's average opposition

Owner ruling 2026-10-09 (UQ-25, refines UQ-17): "can pass a vote alone" is judged against the AVERAGE OPPOSITION of the trailing year — not "nobody else votes" (the round-10 literal reading) and not "everyone else votes no". Uncommitted at the time of writing. Tests: `tests/unit/oracleRegistryConfigUq25.test.ts` (16 tests; with the rule and collector files reverted to HEAD `c6e29db9` and only the new exports stubbed, 14 fail; the other 2 are controls — the fixture's mean, and the getVote ABI decoding Lido's extra word).

| Part | Now (where) |
| --- | --- |
| Rule | `rules.ts` `tokenVoteDecision`: a holder set passes alone iff `yes × 1e18 / supply > minAcceptQuorumPct` AND `yes × 1e18 / (yes + D) > supportRequiredPct`, D = `voting.defense.mean`. The rank shape is unchanged: the weakest passing set of k holders (k = 1: that holder; 2 ≤ k ≤ 10: a k-of-k multisig; more: broadly held). The Lido Agent back-reference (`selfRef`) stays excluded (owner: keep it). |
| D | `admin.mjs` `voteDefense`: `votesLength()` at the classification block, then `getVote(id)` newest first (Multicall3 batches of 25; one eth_call per vote before block 14,353,601) until a vote started before the window (vote ids rise with their start dates). Window: votes STARTED in (block time − 365 d, block time]. Each nay stake is read at the block, so a vote still open counts its nays so far (fewer nays: the fail-closed side). D = floor(sum / count); a vote with no nays counts as 0. Only the nine static words of `getVote` are decoded, so Lido's extra trailing `phase` word is ignored. Cached per (vote app, block) in `.cache/vote-defense-v1.json`. |
| No vote in the window | D = 0 (fail closed), and the rank note says so: "no vote started in the 365 days to <date>: D = 0 (fail closed — no opposition assumed)". |
| Unread history | A failed read (`voting.defenseUnread`) or no `defense` at all (a classification from before UQ-25) makes the decision unread: a read gap, ranked as a plain contract with no delay credit (UQ-18), listed in the head state as "trailing-year vote history not read". The collector then classifies no holders and fetches no holder snapshot for that vote (`enrichTokenVotes`). |
| Card | The rank note names k, D (as a share of supply), the window end and the vote count, e.g. "ONE holder of 0x5a98… can pass a vote alone (k = 1): EOA 0xf977…acec — ranked as it; against D = 0.027 % of supply, the mean nay stake of the 13 votes started in the 365 days to 2026-10-09". |
| Cache | A cached vote classification without `defense` is read again; the holders it had already classified at that block are reused, not classified again. |
| Thresholds | Kept strict, as Aragon `_isValuePct` computes them. The ruling writes "≥"; the chain tests "greater than". They differ only at exact equality (pinned by the round-10 test "the quorum is strict"). Review round 11: equality does occur in the LDO data — at 11,473,299 and 12,341,644 three non-Agent holders hold exactly 50,000,000 LDO (5.000 %); strict gives k = 2, "≥" k = 1. They are plain contracts, so the rank is `[2]` either way. Open owner call UQ-31. |

**Measured (Lido's Voting `0x2e59…618e` at 26,152,213, every value cross-checked with a raw eth_call):** 13 votes started in the trailing year (ids 193–205, 2025-10-16 → 2026-09-16); nays 3,628,764.6 LDO in total, almost all in two votes (193: 1,396,044; 200: 2,229,704); D = 279,135.7 LDO = 0.0279 % of supply (the card shows it truncated, 0.027 %). `0xf977…acec` (an EOA) holds 6.078 %: above the 5 % quorum, and 60.78M / (60.78M + 0.28M) = 99.5 % support. So k = 1 and the Lido vote still ranks as an EOA; D would have to exceed 60.78M LDO (218 × the measured mean) to change that. Over all 118 cached LDO blocks (2020-12 → 2026-10), D peaks at 0.069 % of supply (2021) and changes k at none of them: k = 1 at 116 and k = 2 at the two 2020–21 blocks, with D or without. The support test never binds there, because D stays far below the 5 % quorum share any passing set must already hold. The first block, 11,473,299 (2020-12-17), has no vote in its window: D = 0, and its note says so. The 118 D values are cached in `.cache/vote-defense-v1.json`. **UQ-25 therefore changes no stored verdict; it changes only the rank notes**, which now name D, the window, the vote count and k. The stored cards were not re-collected (KG-4).
