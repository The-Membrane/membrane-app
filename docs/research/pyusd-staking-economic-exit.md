# PYUSD StakingVault economic exit assay v1

The frozen August subject remains `PYUSD → StakingVault [wYLDS]` at `0x19eb…f7f6`. It is a **mismatched route label**: the deployed StakingVault is Hastra PRIME; its underlying is wYLDS, and the wYLDS YieldVault's underlying is USDC. This work does not edit the frozen seed or infer a USDC→PYUSD conversion. The public UI must continue to treat a PYUSD payout as unassessed.

```text
PRIME shares (StakingVault)
  └─ holder redeem → wYLDS       exact-holder eth_call assessed
       └─ requestRedeem → pending request   separate user transaction
            └─ admin completeRedeem → USDC Transfer to holder   historical receipts assessed
                 └─ USDC → PYUSD             no route attested
```

## Source mechanics

[Hastra's curator guide](https://github.com/provenance-io/hastra-eth-vault/blob/main/docs/CURATOR_INTEGRATION.md) describes instant PRIME unstaking and the admin-gated two-step wYLDS redemption. Its text event table abbreviates `RedemptionCompleted`; the [current YieldVault source](https://github.com/provenance-io/hastra-eth-vault/blob/main/contracts/YieldVault.sol) declares `RedemptionCompleted(address indexed user,uint256 shares,uint256 assets,uint256 timestamp)` and actually transfers USDC from `redeemVault` to the user in `completeRedeem`. The source also permits only one pending request per holder. This study uses the full four-field event signature and checks the actual USDC Transfer in the mined receipt. The deployed implementation is pinned separately from the source description.

## Local collectors

- `node scripts/research/pyusd-staking-economic-exit.mjs`: read-only finalized two-origin snapshot; pins both proxy and implementation runtime hashes, both assets, all four token decimals, holder PRIME balance, max redeem, pause and freeze state, current pending redemption, and exact same-holder `redeem(Q,holder,holder)` eth_call. Q is one tenth of the selected holder's PRIME balance, capped by the positive-balance check. The result is **only** the callable PRIME→wYLDS stage. Separate eth_calls cannot carry simulated wYLDS into `requestRedeem`, and cannot model the administrator's later completion.
- `node scripts/research/pyusd-staking-redemption-history.mjs`: bounded 5,000-finalized-block event discovery on one origin, strict in-range log checks, two matching block headers per found event, then second-origin event and paired receipt reconciliation. It pairs same-user request/completion/cancel sequences, checks shares and assets, verifies event timestamp against block timestamp, and classifies a paid completion during capture only when the completion receipt includes one exact USDC Transfer from the block-end `redeemVault` to that holder. Requests outside the window are left censored; unmatched requests are right censored. **Discovery completeness is not proven** because the second origin does not replay the whole 5,000-block window. Historical proxy implementation/code and same-block `redeemVault` changes were not attested per event, so upgrade eras and intra-block configuration changes remain unverified.
- `node scripts/research/pyusd-staking-redemption-history.mjs --attest-window` attempts a complete second-origin replay in bounded 50-block slices and publishes only on exact raw-log agreement. DRPC answered the found events by block hash but rejected older range queries as narrow as five blocks; the first full-window attempt published nothing. Use another archive-capable independent provider to close this gap.
- Each output goes to an immutable, SHA-linked local ledger under `data/research/venue-signals/`, with no Neon dependency. Both collectors enforce a 1 GiB disk reserve, bounded RPC and file reads, no-follow ledger reads, and no replacement of a numbered file. `--verify` checks ledger integrity and replays request/completion pairing offline. **The history ledger stores receipt digests, not full raw receipts or both raw log responses:** its offline verifier cannot independently reproduce the USDC Transfer classification or the two-origin event comparison. Those payout findings currently depend on live-capture trust and must not be promoted to an independently replayable payout proof. Operator-supplied holder is optional on the economic snapshot; no transaction is sent.

## First live pilot (2026-10-01 UTC)

The first economic snapshot at finalized Ethereum block **26,095,447**, hash `0xec73dacf…cf6e0a4`, was attested by Ankr and DRPC. A recent PRIME Transfer screened an EOA with 4.000000 PRIME. The frozen Q was **0.400000 PRIME** and the same-holder redeem eth_call returned **0.424890 wYLDS**; maxRedeem was 4.000000 PRIME. The StakingVault and YieldVault were unpaused; the holder was unfrozen and had no pending wYLDS request. Snapshot SHA-256: `e131dd233a0393e01d80cfa7b8bcf0aa73e36c011c4f7864fca58ccaece40a80`. This is callable first-stage evidence, not a mined wYLDS receipt, USDC settlement, or PYUSD exit.

The first history snapshot covered **B26,090,480–26,095,479**. During live collection, Ankr discovered **14** request/completion events; DRPC confirmed each discovered event and both providers' receipt material agreed. The capture classified **seven** request→completion episodes from **six distinct holders** as having exact USDC Transfers; one holder appears twice. Observed completion times were **18, 57, 59.2, 69.2, 70.4, 70.4, and 295.4 minutes** (1,080 to 17,724 seconds). History SHA-256: `346bdbbb40f472214705ecd8ef8c1e2a536d51d0292bdf1b368da4a926919a2e`. The sealed row preserves those classifications and receipt digests but not the receipts needed to recheck them offline. These are historical selected episodes, not independent future holder outcomes; they cannot support a probability, likely-duration forecast, or future payout guarantee. Operator timing and compliance are not derivable from vault balance.

## Prospective PRIME first-stage lane

`node scripts/research/pyusd-staking-prospective.mjs --issue|--score|--verify` runs locally without Neon. Each issue screens a previously unused EOA PRIME holder, freezes exactly one PRIME-share Q at one finalized two-origin baseline, and schedules H1/H4/H24/H48/H168 checks. Each score seeks the **first finalized block at or after its target clock**, independently checks that block and predecessor on two origins, pins both deployed proxy/implementation hashes and asset links, then repeats `redeem(Q,holder,holder)` for the same holder and Q. The capture deadline is two hours after each target; a missed-window row requires both finalized heads to have advanced beyond that deadline **and** both origins to return the same canonical header at their common finalized height. A sealed issue or score remains terminal if the separate attempt log fails, and an issue/horizon score key cannot be published twice. No simulated first-stage result is a mined wYLDS receipt or a USDC/PYUSD payout. One issue is one holder episode; multiple horizons remain correlated.

The first prospective issue sealed at **2026-10-01 06:20:13 UTC**, baseline B26,095,543 (Ankr+DRPC), Q **0.400000 PRIME**, baseline `prime_to_wylds_callable`. Its issue SHA-256 is `d51bfc0a43b45e6ecf3dd60c70585ce93163106adae8d25b735665f276c8ce90`. At the October 4 offline replay, the ledger had **4 distinct-holder issues and 8 scores**: six measured first-stage simulations and two missed-window censors. The single native holder-exit campaign now schedules this first-stage issue/score lane; local free space is below its 1 GiB plus 256 KiB pre-network guard, so it has collected no new live row in this session. The local-only `/api/carry/pyusd-staking-prime-evidence` endpoint exposes coarse counts and `calibratedForecast:false`, omitting the holder, Q, target clocks and private proof. The frozen PYUSD route remains a label for the tracked subject, not an attested PYUSD payout.

The separate [wYLDS queue request-window issuer](../../scripts/research/pyusd-wylds-queue-issue.mjs) remains an unscheduled intake instrument with **zero live windows and zero prospective requests**. It seals contiguous two-origin five-block request windows, including empty windows, with earlier history explicitly unobserved. Its whole-run 60-second deadline now interrupts in-flight RPC, a shared 480-call cap spans the run, dense windows split at block boundaries, and compact block witnesses prevent ordinary transaction arrays from filling a row. A single block with more than 12 requests still fails closed. It replays the full archive once per run, so sustained throughput and long-term replay cost need measurement before activation.

The new [wYLDS queue lifecycle collector](../../scripts/research/pyusd-wylds-queue-lifecycle-v2.mjs) is also **offline-tested only, with zero live windows**. It discovers request, completion, and cancellation events in contiguous two-origin finalized windows; keeps raw successful receipts; joins exact-holder shares/assets episodes with left and right censoring; and checks a same-transaction USDC Transfer from the block-end `redeemVault` to the holder. Its claimed intermediate payout does not prove intra-block vault configuration, first recovery of executable exit ability, or final PYUSD receipt. It has a hard 90-second run deadline, bounded windows/RPC/row size, and an offline streaming verifier. Each sealed row commits to its derived post-window state; the compact operational checkpoint must match the sealed tip before resuming, while the full verifier remains the publication gate. The collector reports elapsed time, RPC calls, blocks advanced, and finalized-head lag for a cadence pilot without exposing holder data. A single block with more than 12 lifecycle events remains a hard blocker. The existing single Mac campaign allows up to 550 seconds for another evidence lane inside a 590-second tick, so a queue scan cannot simply be added to every tick without a measured cadence and runtime redesign.
