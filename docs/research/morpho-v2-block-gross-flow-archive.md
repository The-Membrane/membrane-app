# Morpho VaultV2 block-major gross-flow archive v1

This is a separate retrospective research lane from the immutable RLUSD single-vault 64-block pilot and the prospective Morpho flow ledger. It loads the exact frozen 49-subject route manifest through `loadMorphoFlowSubjects`; the manifest's pinned route, seed, board, and display hashes are checked there. The enrollment freezes a campaign start boundary and finite end block/hash. A resume rereads both chain boundaries and rejects a changed end hash. Each bundle covers at most 64 contiguous blocks for all 49 subjects; each provider query covers at most 10 blocks and passes all 49 addresses in one `eth_getLogs` filter. All three event streams are queried separately and as a combined topic set, then compared byte-for-byte after canonical normalization across two RPC origins.

Run a read-only capability probe before live capture:

```sh
CARRY_MORPHO_ARCHIVE_ORIGINS=rpc.ankr.com,rpc.flashbots.net node scripts/research/record-carry-morpho-v2-block-archive.mjs --probe
```

`CARRY_MORPHO_ARCHIVE_ORIGINS` selects two hostnames present in `RECORDER_RPC_URLS`; it never prints credential-bearing URLs. `--capture` repeats the probe before publishing enrollment and will stop if provider sets disagree. `--verify` is fully offline and requires every bundle through the frozen campaign end. `--verify-partial` reports incomplete progress without treating it as complete. A successful pilot would use `--capture` once for the default 64-block campaign and then `--verify`.

For a longer finite campaign, `--capture --end-block N` freezes an explicit finalized end block at enrollment (up to 250,000 blocks after the timestamp-selected start), then captures one 64-block bundle per invocation. Subsequent invocations read the frozen enrollment end automatically. The first 64-block pilot below used the default bound.

Each canonical, SHA-256 bound bundle includes the previous digest, global block/hash cursor, both origins' raw logs and boundary/event headers, and one vault row for every frozen subject. Deployed vaults get explicit zero counts for Deposit, Withdraw, and ForceDeallocate in quiet ranges. `predeployment` and `unavailable` are distinct, with no invented zero-event observation. An `observedFromBlock` field limits an in-range deployment's coverage. The local receipt is stamped only when the bundle is made. Enrollment and bundles publish via exclusive hard-link from a synced temporary file; the offline verifier rejects unknown, stranded, missing, orphan, noncanonical, oversized, misordered, partial, or route-drift files. Writes enforce a 16 MiB per-file cap and at least 1 GiB remaining disk.

## First provider capability measurement (2026-10-01)

The first read-only historical anchor was block 25,880,284, with a tentative 64-block pilot ending 25,880,347 (`0xc2d23f2feb2eac96439f315d4e7f6370ac75eec1c5a72adcb1e9dea0da05b773`). Both Ankr and Flashbots accepted a 49-address, 10-block `eth_getLogs` filter for each separate event topic and the combined topic set. Ankr returned one raw Withdraw log in the first slice (response JSON 1,479 bytes, 411 ms for four calls); Flashbots returned zero (53 bytes, 163 ms). The differing log is vault `0xbeef0c075da5d01112ae5cf34d257074fb5ddb2f`, block 25,880,284, transaction `0x95a851dead52c757ff67473ab9a23cd09986febc03ab3d71d82a5bf72f331e85`. Ankr, Alchemy, and Infura each returned that log with a single-vault and a 10-vault filter; Flashbots returned zero even for the single vault. This is a concrete omission by the Flashbots RPC on that historical query. The collector now rejects cross-origin disagreement before writing.

QuikNode initially returned HTTP 413 / RPC `-32615` on a 10-block query because its configured plan limits `eth_getLogs` to five blocks. The collector now partitions QuikNode's ten-block canonical slices into two five-block requests; the later read-only Ankr/QuikNode probe agreed, although a full bundle still met QuikNode HTTP 429. DRPC returned routing/state errors, and MEV Blocker failed transport. A later 49-address, 10-block Ankr+Alchemy probe agreed (zero logs in blocks 25,880,300–25,880,309; response JSON 53 bytes per origin, 225 ms / 185 ms for four calls). This pair captured the first live all-49 bundle across blocks **25,880,301–25,880,364**. It has seven slices, 49 deployed vault rows, six Deposit logs, six Withdraw logs, zero ForceDeallocate logs, and 54,293 canonical bytes. The bundle SHA-256 is `187294b4893e9566c4f2b9b79e8e7ebe5141ec5d0a5c0a7d0c85f0bcc7fc7bbb`; offline `--verify` returned `complete=true`, one bundle, 64 covered blocks, and 12 events. Hostname difference alone does not prove organizational independence; the archive labels agreement as provider attestation, not certified completeness.

The archive records gross vault contract events. A Withdraw does not prove ERC20 settlement to the holder, and ForceDeallocate may represent internal vault movement. Every bundle states `researchOnly=true`, `prospectiveValidated=false`, and `holderExecutableExit=false`. These historical receipts must not count toward prospective holdout or same-holder payout evidence.

## Immutable v2 archive campaign

The v1 pilot enrollment above is closed at block 25,880,364. The v2 campaign has a separate study identifier and root, `data/research/venue-signals/local-morpho-v2-block-flow-v2`. It verifies the v1 archive before every run, starts at the pilot's exact next block 25,880,365, stores the pilot tip SHA-256 in its enrollment, and freezes one finalized end block/hash. It cannot move the start or extend the end after enrollment. The first enrollment froze end block **26,095,320**, hash `0xd0157a367fa9ab12e25ac6883d8ada269dea7778197e35050aa8634393a6c9c4`; that is 214,956 campaign blocks. This is a finite ~30-day retrospective window, not an indefinitely sliding lookback.

Each `--campaign-tick` validates the predecessor and all existing bundles offline, reads two origins, and publishes **at most one bundle of up to 512 blocks** in slices no wider than ten blocks. Ankr and Alchemy agreed on the first 10-block 49-address probe (eight gross events each). The first live bundle covered 25,880,365–25,880,876, with 100 raw events, SHA-256 `8ea0d198f5f90ae87b9f6dc9fdb5f51e8b719ccdaeb74b6eb13c255c0fbdaece`. Alchemy then returned RPC code 429 during a second 512-block attempt. Nothing was published from that failed attempt. The native tick now requests 128 blocks per bundle, which succeeded twice: the first three bundles total 768 blocks and 194 events, tip SHA-256 `9254097f6a85ce0335bb2d1dfd9c3afe863460e4feb6963ed81cb64aba7ea082`. The full 30-day archive remains incomplete.

```sh
node scripts/research/record-carry-morpho-v2-block-archive.mjs --campaign-verify-partial
node scripts/research/record-carry-morpho-v2-block-archive.mjs --campaign-verify
```

The first command verifies a partial chain; the strict second command fails until the end hash is reached. The native Mac `com.membrane.carry-morpho-block-archive` launchd job runs `scripts/carry-morpho-block-archive-tick.sh` every five minutes. It has a nonblocking single-process lock and a 240-second hard bound. A failed RPC or provider disagreement leaves the cursor unchanged and yields a nonzero job exit; the next tick retries that same range. Each bundle is published only after all 49 subjects and both origin witnesses agree. The 1 GiB disk floor and 16 MiB per-file limit remain enforced. At the 2026-10-01 09:25 UTC checkpoint, standalone partial replay accepted **21 bundles, 2,944 covered blocks, and 600 gross events**. Alchemy returned repeated HTTP 429 on 128-block ticks. Infura agreed with Ankr on the next ten-block probe but returned HTTP 429 on the full tick. QuikNode accepted the same ten-block probe split into five-block requests but also returned HTTP 429 on the full tick. Two consecutive 64-block Ankr/Alchemy captures then succeeded. A native `launchctl kickstart` on the same setting exited zero and sealed another 64-block bundle; standalone replay accepted **22 bundles, 3,008 blocks, and 610 gross events**. The native job now requests 64 blocks per tick. The full campaign still requires roughly 212,000 more blocks and may take many days at this rate. The recorder checks disk before each publication rather than relying on an estimate.
