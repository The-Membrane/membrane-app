# scrvUSD flow: independent-provider sidecars

The primary scrvUSD flow receipts remain immutable. `scripts/research/scrvusd-flow-second-provider.mjs` queries a supplied HTTPS RPC URL and writes one sealed sidecar plus the exact secondary receipt bytes keyed by the primary receipt SHA. It reuses the primary collector's finalized-head, chain ID, vault `asset()`, combined/per-stream log, event ABI, event-block hash, and boundary recheck rules in an isolated temporary directory. That temporary directory is removed after each attempt; the verified secondary receipt is retained separately. The primary receipt and its `rpcHost` never change.

Each sidecar binds both the logical and physical SHA of the primary and retained secondary receipts, source identity, exact finalized range and block hashes, exact Deposit/Withdraw event set (including empty sets), two RPC hosts, and a local observation clock. `auditSidecars` re-reads and validates both receipt sets, rejects gaps, unexpected or altered sidecars, and requires one sidecar for every receipt before returning `certified: true`. The caller may request a block interval; the primary ledger must cover it. The code binds the second hostname to the URL it queries and refuses HTTP redirects. A URL hostname difference **does not prove organizational or infrastructure independence**; the operator must verify provider ownership separately. The local clock is not an external first-availability attestation.

The module is offline-testable with an injected fetch transport; it performs no network work on import. Sidecars record whether native URL-bound fetch or an injected transport performed the read. An audit with any injected transport returns `certified:false`. To capture real sidecars, an operator must explicitly supply a second HTTPS RPC URL and the matching primary receipt directory. No live RPC was called here. The collector's 1 GiB disk reserve remains in force, and the current machine is below it. There is no schedule or automatic backfill in this module.

This certification means two queried providers agreed on the event set at the checked finalized boundaries. It does **not** establish executable same-holder exits, vault liquidity, future duration, or that all possible providers are correct. Any maximum gross/net window should remain historical flow context; a public exit statement needs the other route and holder evidence independently.
