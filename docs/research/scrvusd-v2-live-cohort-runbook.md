## Installation order

1. Provision a dedicated login named by `SCRVUSD_SCHEDULE_PUBLISHER_ROLE`, with a separate password and `SCRVUSD_SCHEDULE_PUBLISHER_DATABASE_URL`. Keep the owner/migration credential in `SCRVUSD_SCHEDULE_MIGRATION_DATABASE_URL`. The publisher must have no superuser, createdb, createrole, bypassrls, database/schema CREATE, or owner membership. Neon may automatically give the creating owner one `ADMIN true, INHERIT false, SET false` membership in the new role; the preflight and runtime audits allow exactly that shape and no other inbound member.
2. Inspect the target database for existing or partial `scrvusd_now_*` objects and existing role grants. The migrations are first-install and additive; they refuse a partial predecessor. Apply `--apply`, then `--apply-attempts`, then `--apply-asof` with the same owner login. Each step is transactional and creates no role or grant.
3. Grant the dedicated publisher `USAGE` on `public`, `SELECT` on the twelve protected tables, and `EXECUTE` on the twelve exact functions listed in `FUNCTION_SIGNATURES` in `scripts/apply-scrvusd-now-schedule-ddl.mjs`. This includes `scrvusd_now_manifest_visibility` and `witness_scrvusd_now_manifest(text)`. Grant no direct writes and no broad function execution. Run `--audit-publisher`, `--audit-attempts`, and `--audit-asof` with the publisher connection. All three must return `passed:true` before using the credential for publication or slot work.
4. Publish a future hourly manifest with enough lead for publication, confirmation, and the separate committed manifest-visibility witness to finish at least two hours before its first slot. Then run one opt-in slot. The runner requires four starts, capture floor, source-start gate, four results, run confirmation, and a separate run-visibility witness. A score is built only after its capture deadline, replayed, recorded exactly, and separately witnessed. Inspect each receipt and any failed/abstained arm; a process exit code alone does not establish coverage.

## Forecast availability time

The local v2 `issuedAtUtc` precedes the four-arm run confirmation and its visibility witness. The witness proves the sealed issue was available **by `runVisibleAtUtc`**; it does not prove that this was its first moment of availability. A nominal target such as `issuedAtUtc + 1h` may have less than one hour of certified lead when the run becomes visible. Store `targetUtc - runVisibleAtUtc` as the **certified minimum remaining lead** for every arm; do not call it exact first-availability lead. The pilot's 1h/2h/24h/7d arms are measurement checkpoints, not a product limit; a later forecast can accept any horizon supported by enough measured outcomes. A run witness after its earliest issued target is rejected. A historical as-of view includes an issue only after its run witness and a score only after its exact score witness. The separate `readWitnessedBoundLabelsWithPgV2` path reconciles all DB arms inside witnessed runs with retained local receipts; pre-witness slots remain outside that label denominator, so full cohort completeness and chronological backtest eligibility remain false. The older retrospective reader remains available for descriptive research. Neither path produces a calibrated forecast.

Its start/result/partial/missed statuses are retrospective timestamp diagnostics; later commits can revise their apparent state at an earlier cutoff. `listWitnessedCohort({asOfUtc})` reconciles four-arm results only for runs with a visibility witness by the cutoff.
